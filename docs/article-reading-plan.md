# 본문 기반 기사 설명 — 현행 사양과 적용 이력

## 현행 사양 (2026-10-16)

이 절은 현재 코드 기준이다. 아래 「최초 적용 계획과 과거 검증 이력」은 당시 작업 기록으로 보존하며, 현재 설정·배포 상태를 뜻하지 않는다.

| 항목 | 현재 값·동작 | 기준 파일 |
|---|---|---|
| 후보·최종 기사 | 전처리 최대 110건 → 섹션 균형 후보 60건 → 최종 최대 20건(+예비 6건, 읽기 총 26건 이하; 2026-10-20 변경) | `config/sources.ts`, `lib/edition-curation.ts` |
| 본문 입력 | 기사당 최대 600자, 전체 11,000자. 남은 예산을 남은 기사 수에 나눠 배분 | `ARTICLE_READING`, `shareChars` |
| 설명 길이 | 한국어 공백 포함 150~190자, 영어 200자 이내 목표. 근거 부족 시 더 짧게 작성 | `config/prompt.ts` |
| 핵심 구절·용어 | 언어별 핵심 구절 1~2개(각 2~60자), 판 전체 용어 최대 12개. 본문 구절과 용어를 함께 강조 | `lib/curate.ts`, `components/Glossary.tsx` |
| 요청 제한 | 동시 4개, 요청당 8초, 본문 단계 전체 30초, 리다이렉트 최대 3회 | `ARTICLE_READING` |
| 크기·압축 | 응답은 압축 전·해제 후 각각 1.5MB. gzip·deflate·Brotli 처리 | `lib/read-articles.ts` |
| 호스트 간격 | 같은 호스트는 직렬 요청, 최소 250ms와 robots crawl-delay 준수 | `lib/read-articles.ts` |

공통 `CRITERIA`·`SELECTION_PROMPT`·코드의 기사 상한은 모두 20건으로 일치한다. 과거 호의 기사 수·설명 길이는 현재 목표와 다를 수 있다.

### 공개 원문과 실패 처리

- 긴 RSS 본문·논문 초록을 우선 활용하고 부족하면 공개 HTTPS HTML을 읽는다. GitHub는 README, HF 모델은 모델 카드를 사용한다.
- Google News의 공개 원문 링크를 우선 확인한다. 중계 페이지 접근 제한·링크 부재 시 공개 Bing News RSS를 기사당 한 번 조회하고, 언론사 도메인이 있으면 도메인과 제목을 대조한다. 도메인이 없으면 제목 일치 기준을 강화한다. 검증한 공개 원문 한 개만 읽는다.
- 검색과 원문 모두 공개 주소·DNS·리다이렉트·robots 검증을 거친다. 403·429는 같은 호스트의 추가 요청을 중단한다. 로그인·유료벽·차단을 우회하거나 비공개 RPC·불투명 링크 해독을 사용하지 않는다.
- 실패하면 피드 설명을 사용한다. 모달에서 주소 미확보·검색/사이트 수집 제한·요청 제한·인증·유료벽·시간·압축·크기·추출 실패를 구분하고, 알 수 없는 이전 사유는 일반 안내를 쓴다. 공개 원문 링크를 따라간 요청 실패는 `publisher-`로 구분한다.
- `_tmp/article-reading/<KST 날짜>/`에 URL별 성공·실패를 캐시한다. 전체 시간 초과는 캐시하지 않는다. 새 CI 러너의 캐시 재사용은 보장하지 않는다.

### 데이터와 화면

- `RawItem.content?: string`: 수집 중 긴 본문·초록. `RawItem.publisherUrl?: string`: RSS가 제공한 언론사 주소. 스냅샷에는 저장하지 않는다.
- `ReadingInfo`: `{status: "body" | "snippet", via: "rss" | "web" | "readme" | "model-card" | "abstract" | "snippet", chars: number, reason?: string, url?: string}`. `url`은 확인된 공개 원문이며 코드에서만 채운다.
- `Item.highlights?: {ko: string[], en: string[]}`는 실제 요약의 핵심 구절이다. 용어는 `glossary`와 대조해 함께 강조하고 겹친 범위는 합친다. `reading.url`이 있으면 모달의 원문 링크에 우선 사용한다.
- 모달은 종이 질감을 유지하고 본문·용어·다른 출처를 간격으로 구분한다. 용어와 다른 출처가 모두 있을 때만 두 영역 사이에 선을 표시한다. 실무 관점은 본문에 녹이며 별도 시사점 영역은 없다.
- 리더 변경만으로 기존 스냅샷 본문이 바뀌지 않는다. 기존 기사를 새 근거로 쓰려면 재확인·설명·핵심 구절·용어·읽기 상태를 함께 갱신해야 한다.

## 최초 적용 계획과 과거 검증 이력

다음 내용은 2026-10-15 당시 계획·검증 기록이다. 미완료 체크 항목과 커밋 금지 문구도 당시 상태이며, 현행 상태는 위 절을 기준으로 한다.

목표: 기존 수집 파이프라인에서 약 20건을 먼저 선별하고, 해당 글의 본문 근거로 설명 작성. 커밋·푸시 없음. 기존 UI·일간 발행 변경 유지.

구조: 수집·전처리 → 짧은 후보로 ID 선별 → 선별된 글의 RSS/HTTP 본문 확보 → 제한된 본문 입력으로 최종 설명. 별도 서비스·브라우저 자동화·차단 우회 없음.

### 상한과 수집 원칙

- 기사 최대 20건, 기사당 근거 텍스트 600자, 최종 근거 텍스트 전체 9,000자(토큰 예산 R3, 2026-10-15; 당초 1,500자·30,000자).
- 본문 HTTP 동시 실행 4개, 요청당 8초, 본문 확보 단계 전체 30초.
- 공개 HTTPS 주소만 접근. 사용자정보·비표준 포트·사설/로컬 IP 금지. DNS와 리다이렉트 주소 검증, 실제 연결 주소 고정.
- 같은 호스트에 요청을 몰지 않음. robots.txt 확인, 403·429·인증·유료벽·추출 실패는 우회나 재시도 없이 snippet으로 폴백.
- RSS 긴 본문을 먼저 활용. GitHub는 README, HF 모델은 모델 카드, 논문은 이미 받은 초록 우선. Google News는 페이지에서 확인 가능한 원문 링크만 사용, 비공개 RPC/차단 우회 없음.
- 추출 HTML은 스크립트·외부 리소스를 실행하지 않음. 모델에는 원문을 지시가 아닌 근거 데이터로 전달.
- 원문 실패 여부와 이유는 스냅샷·로그에 기록. 모달에는 피드 설명임을 간단히 표시.
- 입력·출력 사용량, 단계별 시간 기록. 본문은 로컬 캐시로 같은 URL 당일 재실행 시 재요청 최소화.

### 공유 인터페이스

- `RawItem.content?: string`: 피드/초록에서 확보한 긴 본문. 스냅샷에는 저장하지 않음.
- `ReadingInfo`: `{status: "body" | "snippet", via: "rss" | "web" | "readme" | "model-card" | "abstract" | "snippet", chars: number, reason?: string}`.
- `Item.reading?: ReadingInfo`: 모델이 아닌 코드에서 채움, 기존 스냅샷과 호환.
- `readArticles(items: RawItem[]): Promise<Map<string, ArticleEvidence>>`, `ArticleEvidence = {text: string, reading: ReadingInfo}`. `lib/read-articles.ts`에서 export.
- `ARTICLE_READING` 상수는 `config/sources.ts`에서 export. maxArticles 20, articleChars 600, totalChars 9000, concurrency 4, requestTimeoutMs 8000, totalTimeoutMs 30000, maxBytes 1500000, maxRedirects 3, minBodyChars 300, perHostDelayMs 250.
